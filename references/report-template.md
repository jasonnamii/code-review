# 리뷰 리포트 템플릿 — 쉽고 · 스캔되고 · 바로 고칠 수 있게

개발자가 **스캔만 해도** 무엇을·왜·어떻게 고칠지 아는 MD 리포트. 어려운 말 금지(아래 "쓰지 말 것"). 묶음은 빠짐·겹침 없이(MECE).

> ⛔ **리포트 ≠ 게이트.** 리포트는 게이트에서 **우선순위 + 웨이트를 받은 뒤** 출력하는 최종본이다. 각 항목엔 `file:line` + 패치/방향이 들어가 바로 착수 가능해야 한다.

## 작성 5원칙
1. **쉬운 말** — RED·P0·멱등성·디텍터·신뢰도·축 같은 내부 용어를 본문에 쓰지 않는다. 풀어 쓴다("같은 요청 두 번 와도 한 번만 처리되게").
2. **위치부터** — 모든 항목은 `path/to/file.ts:42`(클릭 가능)로 시작. 어디인지 0초에 알게.
3. **심각도는 순서로** — P0/P1 라벨 대신 섹션 순서(🔧 먼저 / 🟡 곧·나중 / 🎨 취향)로. 위험한 게 위.
4. **왜+어떻게 한 쌍** — 각 항목: 한 줄 문제 + 한 줄 이유(터지는 조건) + 패치/방향. "왜 버그인지"와 "어떻게 고칠지"가 같이.
5. **확신 솔직히** — 확실하지 않으면 "확인 필요"로 표시. 단정과 추정을 섞지 않는다.

쓰지 말 것: RED, P0/P1/P2, 멱등성(→"같은 요청 두 번"), 디텍터, 적대적 검증, 신뢰도 상/중/하(→"확인 필요"), 축, TOCTOU(→"동시에 들어오면"), saga(→"실패 시 되돌리기). (→ 쉬운 말로 번역)

```markdown

## 🔧 먼저 고칠 것 (머지 전)
*지금 안 고치면 버그·사고로 이어지는 것.*

### 1) `src/user/cache.ts:42` — 같은 사용자를 동시에 조회하면 DB를 두 번 친다
- **문제**: 캐시에 없을 때 DB를 읽는데, 두 요청이 동시에 미스 나면 둘 다 DB 조회 → 순간 부하
- **언제 터지나**: 인기 사용자 첫 조회, 캐시 만료 직후 동시 접속
- **이렇게**:
  ```diff
  - const u = await db.getUser(id)
  - cache.set(id, u)
  + const u = await cache.getOrLoad(id, () => db.getUser(id)) // 동시 미스 1회로 합침
  ```
- *확인 필요할 수도: 단일 워커면 영향 작음 — 배포 구성 확인*

### 2) `...:NN` — {문제}

## 라이트 양식 — 위에서 빼고 줄임
- `🔧 먼저 고칠 것`(치명·패치) + `🔗 다른 곳도 확인`(핵심만) + `⚖️ 법무` 해당 시.
- 곧·나중·취향은 "이번엔 생략 — 필요하면 표준으로" 한 줄.

## PR 인라인 코멘트 양식 (옵션 — "코멘트로" 요청 시)

> ⚠️ 외부 발행. 게시 전 사용자 확인. `gh pr review {N} --comment` 또는 `gh api`로 라인 코멘트.

- 한 결함 = 한 코멘트. 변경 라인에 정확히 앵커.
- 형식(짧게): `🔧 {한 줄 문제}. {언제 터지나}.` + 제안 코드블록(GitHub suggestion 가능하면 ` ```suggestion `).
- 취향은 `nit:` 접두. 확신 약하면 `(확인 필요)` 명시.
- 요약 코멘트 1개 + 라인 코멘트 N개. 본문 리포트(.md)와 중복 설명 금지 — 코멘트는 짧게.

- [ ] 잘된 점 1~2개로 균형 잡았나
