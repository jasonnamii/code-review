# 워크드 예제 — 입력부터 리포트까지

전 과정을 한 번 통과시킨 예제. 포맷·흐름 참조용. (수치·코드는 예시)

---

## 예제 1 — 백엔드 diff리뷰 (표준)

**입력**: PR diff. `getUser`를 캐시-aside로 변경.
```diff
+ async function getUser(id) {
+   const cached = cache.get(id)
+   if (cached) return cached
+   const u = await db.getUser(id)   // 기존엔 없으면 throw NotFound 였음
+   cache.set(id, u)
+   return u
+ }
```

**Phase 0** — 파트: 백엔드(`service`·`db`). 백엔드 렌즈 로드. 레드플래그 선행: R4(공유 캐시 동시 접근) 후보, R11(반환 계약 변경 — throw→캐시) 후보.

**Phase 0.5 의미 모델** — 의도: 캐시로 DB 부하↓. 자원: 공유 캐시. 상태: 동시 진입. 계약: 기존 `getUser`는 없으면 throw. 본질=**경합 자원 갱신 + 계약 변경**.

**Phase 1 통과기준(발췌)** — 정확성: 없는 id면? / 동시성: 동시 미스 처리? / 계약: 호출자가 null vs throw 어느 쪽 기대? / 성능: TTL·무한증가?

**Phase 1.5 파급** — `getUser` 호출처 3곳 검색: 모두 `try/catch NotFound`로 "없음"을 처리. 새 코드는 `db.getUser`가 throw하면 그대로 전파되나, **존재 시 캐시만** 하고 미존재는 캐싱 안 함 → 매번 DB. 그리고 동시 미스 시 DB 중복.

**Phase 2 발견 + 적대적 검증**
- 🟥 동시 미스 → DB 중복 조회. *반증 시도: 단일 워커? → 배포는 4 인스턴스·멀티스레드 확인 → 결함 확정* [신뢰도: 상]
- 🟥 미존재 사용자 미캐싱 → 존재하지 않는 id 반복 조회로 DB 부하. [신뢰도: 중]
- ✅ 계약: 호출처 3곳 모두 throw 기대 + 새 코드도 throw 전파 → 통과(거짓양성 회피)

**게이트(쉬운 말)**: "먼저 고칠 것 1개(동시 조회 중복), 곧 1개(없는 사용자 반복 조회). 표준/헤비?" → 사용자: 표준.

**Phase 4 리포트(발췌)**
```
## 🔧 먼저 고칠 것
### 1) src/user/service.ts:42 — 같은 사용자를 동시에 조회하면 DB를 여러 번 친다
- 언제: 캐시 만료 직후 동시 접속(인스턴스 4대)
- 이렇게: getOrLoad로 동시 미스를 1회로 합치기 [패치]
## 🟡 곧·나중
| service.ts:44 | 없는 사용자는 캐시 안 해 매번 DB 조회 | 짧은 TTL로 "없음"도 캐시 |
## 🔗 다른 곳도 확인
| order/cache.ts:30 | 같은 캐시 패턴 → 동일 문제 가능 |
```

## 예제 2 — 프론트 diff리뷰 (라이트)

**입력**: `useEffect`로 검색 API 호출 추가.
```diff
+ useEffect(() => {
+   fetch(`/search?q=${q}`).then(r => r.json()).then(setResults)
+ }, [])   // 의존성 비어있음
```

**파트**: 프론트. 렌즈: 의존성·race·cleanup·XSS.
**발견(라이트=치명만)**:
- 🟥 의존성 배열 `[]` → `q` 바뀌어도 재검색 안 됨(stale). [신뢰도: 상]
- 🟥 빠른 타이핑 시 응답 순서 역전(race) → 옛 결과 표시. AbortController/취소 없음. [신뢰도: 상]
- 🟥 `q`를 URL에 미인코딩 결합 → 깨짐/주입. [신뢰도: 중]

**리포트**: 🔧 의존성 `[q]` + 이전 요청 취소(AbortController) + `encodeURIComponent(q)`. (라이트라 곧·나중·취향 생략)

## 예제 3 — 멀티파트 (백엔드 API + 앱)

**입력**: 백엔드가 `/orders` 응답에서 `status` 필드를 enum 문자열→객체로 변경. iOS 앱도 같은 PR.
**핵심은 파트 경계**: 🟥 백엔드 응답 형태 변경 → 기존 앱 버전(구버전 클라)이 `status` 문자열 파싱하다 크래시. *적대적 검증: 강제 업데이트 강제됨? → 아니오 → 결함 확정* [신뢰도: 상]
→ 처방: 필드 추가형(구 `status` 유지 + 새 `statusDetail` 추가)·버전 분기. **파트 경계 계약**을 단일 파트 결함보다 위에 둔다.

## ❌ 거짓양성 회피 예 (반증이 결함을 죽인 경우)
```
후보: profile.ts:20 — user.email 접근, user null이면 크래시
반증: 이 핸들러는 requireAuth 미들웨어 뒤에만 등록 → user non-null 보장(검색 확인)
판정: 거짓양성 → 제외 (또는 [신뢰도: 하] "requireAuth 전제 의존"로 격하)
```
이 한 번의 반증이 리포트 신뢰를 지킨다 — 코드리뷰의 핵심.
