# 시스템 파급 분석 — 변경은 혼자 살지 않는다

**변경 라인 고립 분석 금지**(절대규칙 5). 진짜 버그의 큰 몫은 "바뀐 줄"이 아니라 "그 변경이 깬 주변·호출자·계약"에 있다. 변경이 건드리는 심볼·계약·자원을 식별하고 3방향 + 횡단으로 파급을 추론한다.

> 실제로 읽는다(추측 ✗): 변경된 심볼의 **호출처를 grep/검색**해 실제 코드를 본다. "아마 호출자가 처리할 것"은 거짓양성·누락의 원천.

---

## ⬆ 상류(호출자) — 이 변경이 부르는 쪽을 깨나

변경된 함수·메서드·API·이벤트를 **누가 부르나**? 다음이 바뀌면 호출자가 깨진다:
- **시그니처**: 인자 추가/제거/순서/타입, 옵셔널→필수
- **반환**: 타입·형태 변경, null 반환 시작/중단, 빈 배열 vs null
- **예외**: 새 예외 던짐, 던지던 걸 안 던짐(호출자 catch 무력)
- **부작용·계약**: 사전/사후조건 변경, 멱등성 깸, 동기→비동기

→ 호출처를 검색해 각각 새 계약을 견디나 확인. 못 견디는 곳은 `[파급]` 결함으로 등록.

## ⬇ 하류(호출처·의존) — 이 코드가 부르는 것을 올바로 다루나

이 변경이 **새로 부르는** 함수·API·라이브러리의 계약을 올바로 다루나?
- 그 함수의 실패 모드(예외·null·타임아웃·부분결과)를 처리하나?
- 그 함수의 전제조건(정렬됨·non-null·범위)을 만족시키나?
- 외부 의존(DB·API·캐시)의 다운·지연·레이트리밋에 대비했나?

## ➡ 미래(유발) — 이 변경이 곧 요구할 후속

- 피처플래그 추가 → 정리 시점·기본값
- 임시 마이그레이션 → 후속 백필·구 컬럼 제거
- deprecated 표시 → 제거 일정·호출자 이전
- 새 설정·환경변수 → 문서·배포 환경 반영
→ 결함은 아니지만 **로드맵 제언**으로 남긴다.

## 🔗 횡단 일관성 — 코드베이스 전체와 맞나

- **같은 버그/같은 수정**: 이 결함·패턴이 코드베이스 **다른 곳에도** 있나? (복붙된 동일 로직) → 한 곳만 고치면 나머지가 남는다. 검색해 동반 수정 제언
- **관행 정합**: 에러처리·로깅·메트릭·네이밍·인증 패턴이 기존 관행과 어긋나나
- **설정·플래그**: 새 동작이 설정·피처플래그 누락 시 안전한가
- **국제화·시간대·통화**: 횡단 정책을 따르나

## ⚠️ 꼬임 — 기존 계약·불변식을 깨나

- 기존 불변식(잔액≥0·정렬 유지·유니크) 위반
- 상태머신 금지 전이 허용
- 데이터 계약·직렬화 포맷 하위호환 깸 → 저장된 데이터·진행 중 요청·구 버전 클라이언트
- 무중단 배포 중 구·신 코드 공존 시 충돌

## 멀티파트 경계 (→ `part-lens.md` 멀티파트)

여러 파트를 건드리면 파트 경계 계약을 최우선 파급으로 본다: 백엔드 API 변경 → 프론트·앱이 깨지나, 스키마 변경 → 마이그레이션·구버전 공존, 학습-서빙 전처리 일관성.

## 출력 형식
```
## 🔗 파급 (다른 곳도 확인)
⬆ getUser 호출처 3곳(profile.ts:20·order.ts:55·auth.ts:8) — 예전 throw였는데 이제 null 반환
   → 3곳 모두 null 미처리 → [파급] 결함 등록
🔗 같은 캐시 패턴이 order/cache.ts:30에도 → 같은 동시 조회 문제 동반 수정 제언
⚠️ User 직렬화에 필드 제거 → 저장된 세션 역직렬화 깨짐 (마이그레이션 필요)
➡ 추가한 ENABLE_NEW_CACHE 플래그 → 정리 시점 로드맵
```
