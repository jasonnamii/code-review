# 8축 역추출 엔진 — 코드가 통과해야 할 기준

의미 모델(의도·계약·자원·상태·불변식)을 입력받아 "이 변경이 옳으려면 통과해야 할 기준"을 **체계적으로** 뽑는 질문 체계. 코드의 결함은 거의 전부 이 8축 어딘가에 있다.

**사용법**: 변경의 각 입력·자원·경로를 8축 전부에 통과시킨다. "여기서 정확성은? 동시성은? 에러는?…" — 한 축이라도 건너뛰면 그 자리가 구멍이 된다. 각 항목은 관련성 판정(● 해당 / ○ 부분 / – 무관+사유)으로 적용하고, 결함 후보는 **적대적 검증**을 통과해야 확정한다(`reasoning-method.md` 원칙 4·5).

> 8축 정의 — 정확성·상태/동시성·에러/실패·계약·보안·성능·구조·테스트.

---

## 축 1 — 정확성 (Correctness): "로직이 의도대로인가"

- **로직 정합**: 코드가 실제로 하는 일 = 의도? 조건·부호·연산자 뒤집힘(`<` vs `<=`, `&&` vs `||`, `!` 누락)?
- **엣지·off-by-one**: 루프 경계, 인덱스 `0`·`length-1`·`length`, 슬라이스 끝, 빈 컬렉션, 단일 원소
- **null·undefined·빈값**: null ≠ 빈문자열 ≠ 0 ≠ `[]` ≠ 미정의. 옵셔널 체이닝 빠진 곳, 디폴트값 오류
- **타입·형변환**: 암묵 형변환(`"1"+1`, truthy/falsy), 정수/실수, 부동소수 비교, 오버플로/언더플로, 시간대·통화 단위
- **분기·반환 누락**: 모든 경로가 값을 반환하나? `switch` default? 빠진 `else`? early-return 후 정리 누락?
- **복사 vs 참조**: 얕은 복사로 원본 변형, 가변 디폴트 인자, 공유 참조 의도치 않은 변경
- **순서 의존**: 초기화 전 사용, 선언·호이스팅, 비동기 결과를 동기처럼 사용

## 축 2 — 상태·동시성 (State/Concurrency): "공유·전이는 안전한가"

가장 거짓양성과 진짜 버그가 갈리는 축 — 동시 접근이 실제로 일어나는지부터 확인.

- **레이스·경합 자원**: 읽고-검사-쓰기(check-then-act)가 원자적인가? 공유 변수·캐시·카운터·잔액·재고에 동시 진입? TOCTOU?
- **멱등성**: 같은 요청·메시지가 두 번 와도 한 번만 처리되나? (재시도·중복 이벤트·더블클릭) 결제·생성·전송
- **트랜잭션 원자성**: 다단계 쓰기가 전부-또는-전무인가? 부분 커밋? 트랜잭션 경계 밖 IO?
- **데드락·락 순서**: 락 획득 순서 일관? 락 잡고 외부 호출(긴 점유)? 락 누락/이중 해제?
- **캐시·복제 일관성**: 캐시 무효화 타이밍, 쓰기 후 읽기, 복제 지연(read-after-write), stale 데이터
- **부분 실패·롤백**: 일부 성공 후 실패 시 되돌리나(보상)? 외부 호출 성공 + DB 실패 = 불일치?
- **순서·재정렬**: 메모리 가시성(언어 메모리 모델), 이벤트 순서 보장, 큐 처리 순서

## 축 3 — 에러·실패 (Error/Failure): "실패를 올바로 다루나"

- **삼킨 예외**: `catch {}` 빈 블록, 로그만 찍고 계속, 에러를 null로 변환해 호출자가 모르게
- **미처리·전파**: 던질 수 있는 예외를 호출자가 다루나? 비동기 거부(unhandled rejection)? 에러 타입 구분?
- **자원 누수**: 파일·소켓·커넥션·락·스트림·타이머가 모든 경로(특히 예외 경로)에서 닫히나? `finally`/`defer`/`with`/RAII?
- **타임아웃·행(hang)**: 외부 호출에 타임아웃 있나? 무한 대기·무한 루프 가능?
- **재시도·백오프**: 재시도 대상이 멱등인가? 지수 백오프+지터? thundering herd? 재시도 한도?
- **부분 입력·손상 데이터**: 잘린 입력, 깨진 JSON, 예상 못한 형식에 죽지 않고 처리하나?
- **실패 메시지**: 사용자에게 내부 정보(스택·경로·쿼리) 노출? 에러 맥락이 디버깅에 충분?

## 축 4 — 인터페이스·계약 (Contract/API): "호출자·하위호환을 깨나"

- **시그니처 변경**: 인자 추가/제거/순서/타입, 반환 타입·형태 변경이 **호출자를 깨나**? (Phase 1.5 파급과 연동)
- **계약 위반**: 사전/사후조건, 던지는 예외 종류 변경, null 반환 시작/중단, 부작용 추가
- **하위호환**: 공개 API·이벤트·스키마·직렬화 포맷·DB 컬럼 변경이 기존 클라이언트·데이터와 호환되나?
- **마이그레이션**: 스키마·데이터 변경에 마이그레이션 있나? 롤백 가능? 무중단 배포 시 구/신 버전 공존?
- **기본값·설정**: 디폴트 변경이 기존 동작을 바꾸나? 설정·환경변수·피처플래그 누락 시 안전?
- **반환 계약 일관**: 같은 함수가 때론 throw 때론 null, 때론 빈배열 — 일관된가?

## 축 5 — 보안 (Security, 디텍터): "공격 표면을 늘리나" → `security-detector.md`

- **인젝션**: SQL/NoSQL/명령/LDAP/템플릿 — 외부 입력이 코드·쿼리로 조립되나? 파라미터화/이스케이프?
- **authz/authn**: 권한 체크가 서버에서, 매 요청? 수평/수직 권한상승? IDOR(객체 직접참조)? 인증 우회?
- **비밀값·노출**: 하드코딩 키·토큰·비밀번호? 로그·에러·URL에 비밀/PII 노출? `.env` 커밋?
- **입력 검증·이스케이프**: XSS(출력 인코딩), 경로 traversal, 역직렬화, SSRF, 오픈 리다이렉트, 정규식 DoS
- **암호·난수**: 약한 해시(MD5/SHA1 for password), 예측 가능 난수(security용 `Math.random`), 평문 저장
- → 코드 결함(인젝션·권한·검증)은 처방. **라이선스·규제 적합성 판단은 라우팅**(생성 ✗).

## 축 6 — 성능·자원 (Performance): "불필요하게 느리거나 무겁나"

성능은 측정이 원칙 — 추정 결함은 [신뢰도: 중/하]로.

- **N+1·반복 쿼리**: 루프 안에서 쿼리·네트워크 호출? 배치/조인/캐시로 줄일 수 있나?
- **알고리즘 복잡도**: 불필요한 O(n²)(중첩 루프 내 탐색), 정렬·해시로 개선 가능? 대용량에서 터지나?
- **불필요 할당·복사**: 루프 내 큰 객체 생성, 문자열 누적(`+=` in loop), 전체 로드 vs 스트리밍
- **메모리·누수**: 무한 증가 캐시/리스트, 제거 안 되는 리스너·구독, 큰 객체 장기 보유
- **동기 블로킹**: 이벤트 루프/요청 스레드에서 동기 IO·CPU 무거운 작업, 비동기화 가능?
- **불필요 연산**: 매 호출 재계산(메모이즈 가능), 조기 종료 누락, 과도한 로깅

## 축 7 — 유지보수·구조 (Maintainability): "읽고 고치기 쉬운가" (→승격 원료)

> 여기는 **취향과 결함을 엄격히 구분**(절대규칙 7). 명백한 해악만 결함, 나머지는 "선택/승격".

- **중복(DRY)**: 같은 로직 복붙 — 한 곳 고치면 다른 곳 안 고쳐지는 버그 위험(이건 결함성)
- **응집·결합**: 한 함수가 여러 책임? 깊은 의존? 전역 상태 의존? 부작용 숨김?
- **네이밍**: 이름이 실제 동작과 다른가(거짓 이름은 결함성), 오해 유발?
- **죽은 코드**: 도달 불가 분기, 미사용 변수·import, 주석처리된 코드
- **복잡도**: 깊은 중첩, 거대 함수, 다중 부정, 매직 넘버 — 가독성·버그 온상
- **일관성**: 코드베이스 관행(에러처리·로깅·네이밍 패턴)과 어긋나나

## 축 8 — 테스트 (Test): "검증되나"

- **통과 기준 커버**: Phase 1에서 세운 기준들이 테스트로 커버되나? 새 분기·엣지에 테스트 있나?
- **회귀 위험**: 변경이 기존 동작을 바꾸는데 테스트가 못 잡나? 깨진 테스트를 약화시켜 통과시켰나?
- **테스트 품질**: 단언 없는 테스트, 항상 통과, 구현 세부에 결합, 플래키(시간·순서·랜덤 의존)
- **검증 누락 경로**: 에러 경로·동시성·경계가 테스트 안 됨

## 역추출 적용 예시

**입력 변경**: "캐시에 사용자가 없으면 DB에서 읽어 캐시에 넣고 반환한다." (`getUser(id)` 신규)
**의미 모델**: 의도=캐시-aside 읽기 / 자원=공유 캐시 / 상태=동시 진입 / 계약=`User` 반환(없으면?)

| 축 | 역추출된 기준(=통과 후보) |
|----|------|
| 정확성 | id가 없는 사용자면 반환값은? null? 예외? 캐시에 음수 캐싱(존재안함)도 하나? |
| 상태·동시성 | 동시에 2요청이 같은 미스 → DB 2회 + 캐시 경합(stampede)? `putIfAbsent`/single-flight 필요? |
| 에러·실패 | DB 조회 실패 시 캐시 오염? 예외 전파? 부분 결과 캐싱 금지? |
| 계약 | 호출자들은 null을 다루나? 기존 `getUser`가 throw였다면 계약 바뀜? |
| 보안 | id가 인가 검증 없이 임의 조회 가능(IDOR)? |
| 성능 | 캐시 TTL/무효화? 무한 증가? 미스 폭주 시 DB 보호? |
| 구조 | 캐시 키 생성 로직 중복? |
| 테스트 | 미스·히트·동시미스·DB실패 경로 테스트 있나? |

→ 이 기준들 중 코드가 충족 못 하고 **적대적 검증(동시 진입 실제 발생?)을 통과한 것**이 곧 결함(RED). 단일 스레드 보장 환경이면 동시성 축은 "– 무관(사유: 단일 워커)"으로 제외.
