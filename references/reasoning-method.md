# 지식 기반 추론 방법론 — 린터가 아니라 이해로 본다

이 스킬의 본질은 **변경의 실패 공간을 MECE로 덮고, 진짜 결함만 거짓양성 없이 잡는 것**이지, 코드에서 패턴을 스캔해 표의 행을 꺼내는 게 아니다. 카탈로그·라이브러리·사례집은 **추론의 참조자료(prior·exemplar)**이지 발동 트리거가 아니다. 아래 5원칙이 린터형 퇴화와 거짓양성을 막는다.

> ⛔ 금지: "`eval`이 보이니 인젝션", "`null` 키워드가 있으니 NPE", "TODO 있으니 결함" 같은 표면 매칭. 패턴이 없어도 의미상 결함이면 다루고, 패턴이 있어도 맥락상 안전하면 사유와 함께 제외한다.

---

## 원칙 1 — 이해 먼저 (코드 의미 모델이 모든 추론의 기준점)

축·디텍터·카탈로그를 돌리기 전에, 변경을 **내 말로 의미 모델로 재구성**한다. 이후 모든 추론은 변경 텍스트가 아니라 이 모델 위에서 작동한다.

| 모델 요소 | 묻는 것 |
|---|---|
| **의도(Intent)** | 이 변경이 *무엇을 하려는가*? 커밋/PR이 주장하는 것과 코드가 실제 하는 게 같나? |
| **계약(Contract)** | 입력·출력·전제조건·사후조건·던지는 예외는? 누가 이 계약에 의존하나? |
| **자원(Resources)** | 무엇을 열고·잠그고·할당하나? (파일·커넥션·락·메모리·트랜잭션) 누가 닫나? |
| **상태(State)** | 공유 상태를 읽나 쓰나? 동시 접근되나? 생애주기·전이는? |
| **불변식(Invariants)** | 항상 참이어야 하는 것은? (잔액≥0, 합계=부분합, 인덱스<길이, 정렬 유지) |

이 모델이 잡히면 "이 변경의 본질은 *경합 자원 갱신*이다 / *외부 IO 경계*다 / *권한 게이트*다 / *순수 변환*이다"가 보인다. 그 본질이 어떤 축·사례를 깊게 봐야 하는지를 결정한다 — 단어가 아니라.

## 원칙 2 — 유추로 사례를 쓴다 (언어 매칭이 아니라 구조 매칭)

`bug-pattern-casebook.md`의 사례는 "Python이면 Python 사례"가 아니다. **변경의 구조를 가장 가까운 사례에 사상(map)**한다.

```
새 코드: "캐시에 없으면 DB 조회해 채운다"
  ↓ 구조 추출: 읽고-검사하고-쓰기(check-then-act) + 공유 캐시 + 동시 진입
  ↓ 구조 유추: ≈ TOCTOU 레이스 + cache stampede (언어 무관, 구조가 같음)
  ↓ 패턴 이식: single-flight / 락 / 원자적 putIfAbsent → 이 코드 맥락으로 번역
  ↓ 신뢰도: 구조 동형 + 동시 진입 확인 → [상]. 단일 스레드 보장되면 → 무관(제외)
```

사례는 베끼는 게 아니라 **번역**한다. 구조가 같고 조건이 충족되면 신뢰도 상, 유추가 멀면 중, 새 구조면 하 + 확인 요청.

## 원칙 3 — MECE 커버리지 (빈틈 0 · 중복 0을 논증)

8축 + 디텍터는 "코드가 무엇이 잘못될 수 있는가"의 **MECE 분할**이다. 체크리스트를 소진하는 게 목적이 아니라, **분할이 변경의 실패공간을 빠짐없이 덮는지 논증**하는 게 목적이다.

- **상호배타(ME)**: 같은 결함을 두 축에서 중복 등록하지 않는다. (자원 누수는 에러축 1곳)
- **전체포괄(CE)**: 의미 모델의 모든 입력·자원·상태·실행 경로가 최소 1개 축에서 검사됐는지 확인. 빠진 경로 = 구멍.
- **고유 케이스 의무 산출**: 카탈로그에 *없던*, 이 코드 고유의 결함 후보를 최소 1개 도출한다. 이게 "매칭이 아니라 추론"의 증거다. 못 뽑으면 의미 모델을 다시 본다.

## 원칙 4 — 관련성 스크리닝 (발동이 아니라 판정)

카탈로그·디텍터의 각 항목은 자동 발동이 아니라, 의미 모델에 비춰 **판정**한다.

| 판정 | 의미 | 출력 |
|---|---|---|
| ● 해당 | 이 변경에 의미상 해당 | 통과기준 등록 → 역검증 |
| ○ 부분 | 변형된 형태로 해당 | 맥락 번역 후 등록 |
| – 무관 | 의미상 무관 / 조건 미충족 | **사유 1줄과 함께 제외** (침묵 제외 ✗) |

"무관"도 사유를 남긴다 — 그래야 "안 본 것"과 "보고 뺀 것"이 구분된다. 표면에 패턴이 없어도 모델상 해당하면 ●로 끌어온다(예: `eval` 없는 문자열 SQL 조립도 인젝션 → 보안축 해당). 패턴이 있어도 무관하면 뺀다(예: 상수 문자열 `eval` → 무관, 사유: 외부 입력 없음).

## 원칙 5 — 적대적 검증 (거짓양성 0 — 코드리뷰의 생명)

결함 후보를 단정하기 전에 **반증을 먼저 시도**한다. 반증에 실패해야 결함으로 확정한다. 이게 린터·LLM 리뷰가 가장 자주 깨지는 지점이다.

각 🟥 후보에 다음을 묻는다:
- **재현되나?** 어떤 입력·순서·동시성에서 실제로 터지나? 트리거를 한 줄로 댈 수 있나?
- **이미 막히나?** 호출 전에 검증되나? 타입 시스템·런타임·프레임워크가 막나? 상위에서 try/guard 하나?
- **죽은 경로인가?** 그 분기가 실제로 도달 가능한가?
- **테스트가 잡나?** 기존 테스트가 이미 커버하나?

```
후보: "user.name 접근, user가 null이면 NPE"
  ↓ 반증: 이 함수 호출 직전에 requireAuth()가 null이면 401 throw → user는 non-null 보장
  ↓ 판정: 거짓양성 → 제외 (또는 [신뢰도: 하] "requireAuth 가정에 의존"으로 격하)
```

반증 못 한 결함만 남기고, 확신 정도를 **신뢰도[상/중/하]**로 표기:
- **상** — 재현 경로/입력을 댈 수 있음, 또는 테스트로 증명 가능
- **중** — 코드상 명백하나 실행으로 확인 안 함
- **하** — 맥락·가정 의존, 추론. **단정 금지, "확인 필요"로 제시**

## 종합 흐름 (린터형 vs 추론형 대비)

```
❌ 린터형:  코드 → 패턴/키워드 스캔 → 표에서 일치 행 출력 (거짓양성 다발)
✅ 추론형:  코드 → ①의미 모델(의도·계약·자원·상태·불변식) → ②본질 규정
           → ③구조 유추로 사례 사상 → ④8축+디텍터 관련성 판정(●○-)
           → ⑤MECE 커버리지 논증 → ⑥고유 케이스 도출
           → ⑦적대적 검증(반증 시도, 거짓양성 제거) → ⑧신뢰도 등급 처방
```

라이브러리·카탈로그·사례집이 풍부한 이유는 **추론의 근거를 대기 위해서**다. 근거 없이 단정하지 않고(패턴 매칭), 반증 없이 결함으로 올리지 않으며(거짓양성), 근거를 들어 이 코드에 맞는 답을 준다.
